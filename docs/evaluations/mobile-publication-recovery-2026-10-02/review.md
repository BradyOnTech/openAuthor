# Encrypted snapshot publication: lost-reply repair

The public desktop transport could delete a published snapshot's ciphertext when metadata committed but its HTTP reply was lost. The catch around `mobile_publish_snapshot` treated every exception as nonpublication and issued Storage DELETE. The minimized deterministic regression performs a successful ciphertext upload, commits the metadata in its injected HTTP boundary, loses the reply, and checks that the exact uploaded ciphertext remains. Before repair it became `null`: one failing test, nine other cases skipped. The broader outcome matrix produced 26 failures and eight passing existing cases before the repair.

Diagnosis hypotheses, ranked before repair:

1. The cleanup catch equated failed response delivery with rolled-back publication. Prediction: upload and metadata commit succeed, then a lost reply triggers DELETE on that object's exact path. The minimized public-path regression confirms this.
2. Upload failed before metadata publication. Prediction: no committed metadata exists. The regression's committed flag and successful upload rule this out.
3. A retry or identity collision removed another object. Prediction: multiple publication calls or a different deleted path. The minimized regression submits one publication for one exact identity; later collision/concurrency controls test that separate hazard explicitly.

The repair retains successfully uploaded ciphertext after every publication error, including explicit 403 rejection. It makes one authenticated read-only lookup through the existing snapshot-list RPC, without repeating publication. An exact row can confirm committed metadata only when all 14 immutable fields match: snapshot/project/revision/key/schema, object bucket/path/length/SHA, encrypted manifest algorithm/nonce/ciphertext/SHA and publishing device. A successful publication response undergoes the same comparison. Storage 409 is reconciled through the same positive-only readback; that status alone never proves successful publication.

The SQL contract at `supabase/migrations/20260830190000_mobile_encrypted_sync.sql:1085` preserves exact publication idempotency. Its read API at line 1111 returns only the newest 100 eligible manifests and filters them by the requesting device's current key envelopes. A missing result cannot prove absence, and it can race another in-flight commit. Current Storage DELETE has no atomic manifest/publication fence. Consequently this bounded patch performs no post-publication cleanup deletion, even after a rejected request. Errors distinguish that rejected request from the still-unconfirmed persisted state, explain ciphertext retention, and make no automatic retry.

Validation passed 61 tests across the transport, sync service, hosted coordinator and key-provisioning modules, TypeScript checking, and the original minimized regression. Controls include exact committed recovery after lost reply/invalid successful JSON/incomplete success body/500, unreadable or unavailable readback, missing/wrong/duplicate identity, every immutable metadata-field mismatch, delayed concurrent commit after 403, and existing-object collisions. Exact object and singleton row-array success require no additional readback; zero/multiple/null/nested row arrays cannot acknowledge without positive reconciliation. Original red/green output and exact source hashes are in `verification.json`. Independent review found no blocking issue in this bounded data-loss guarantee. No debug instrumentation, deployed network, live provider, author book data or UI/port-4173 change was used.

Positive acknowledgement proves exact committed metadata. It does not perform a fresh Storage object download/hash check or certify a deployed PostgREST configuration. [PostgREST's official resource representation documentation](https://docs.postgrest.org/en/v16/references/api/resource_representation.html#singular-or-plural), inspected October 2, explains that default JSON results use arrays even for one row, with singular objects available through content negotiation. The transport accepts either an exact object or strictly one exact row in an array. Deployed API/bucket/RLS acceptance remains required. Ciphertext may now remain orphaned after genuine rejection; trusted orphan-inclusive cleanup, deletion freeze/finalization, continuous voice policy and lost-device UX remain separate work.
